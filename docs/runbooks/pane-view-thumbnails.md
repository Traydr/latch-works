# Pane View Thumbnail Plan

Pane View already reads thumbnail rows from the `thumbnails` table and renders
`/api/media/:mediaId/thumbnail?size=...` when a row exists. The blank cards in
the UI mean the thumbnail generation and delivery pipeline is not complete for
the synced web archive yet.

## Target Shape

1. Generate thumbnails during sync or as a queue after sync.
2. Store thumbnail objects separately from originals.
3. Keep the Pane View API as the authenticated decision point.
4. Let a CDN serve bytes after Pane View authorizes a request.

## Recommended Bunny CDN Approach

- Store generated thumbnails in Bunny Storage or S3-compatible storage with
  deterministic keys such as `thumbnails/{mediaObjectId}/{size}.webp`.
- Keep thumbnail metadata in the existing `thumbnails` table: media object id,
  size, dimensions, status, and object key.
- On `/api/media/:mediaId/thumbnail`, require the Better Auth session, check
  that the library entry exists, then return either:
  - a short-lived signed Bunny token URL, or
  - a proxied response for small thumbnails if token auth is not ready.
- Do not expose raw object keys or long-lived public URLs in the library API.

## Auth Options

- **Signed CDN URL:** best default. Pane View checks Better Auth, signs a URL
  that expires quickly, and the browser loads directly from Bunny.
- **Pane View proxy:** simplest and most private, but every thumbnail byte hits
  the app server.
- **Separate thumbnail service:** useful later if generation becomes expensive.
  It should trust only service credentials, never browser cookies directly.

## Open Questions

- Whether thumbnails should be generated by Lockstep during upload or by a
  Railway/background worker after sync.
- Whether animated images and videos need static poster frames, short animated
  previews, or both.
- Whether Bunny token auth is enough for private thumbnail URLs in the current
  deployment model.
