# Oriel: the optimization round of 2026-11-05

Going to the next set in Duplicates now draws every tile on its first frame: about 5 ms, down from
about 55 ms for stills and about 500 ms for videos, at the same CPU and memory. What a decision
reads again costs 30 % less CPU on a catalog of 22,000 files. The largest cost left is AV1 decoding in Tidy's first analysis.
Hardware decoding cuts its CPU by 3 times and gives the same bytes on 998 of 998 stills. The owner
chose to have it, and the second round adds it for prints, on macOS only.

Machine: the M5 Pro (18 cores, 48 GB), not quiet: other agents built and ran the app throughout.
Every comparison was interleaved within rounds, and each row states its load average. Compare
these numbers only with each other, never with the [scorecard](scorecard.md), which came from a
quiet machine. Builds are `cargo build --release`, not the `dist` profile.

## Fixtures

All synthetic; none comes from the owner's library.

- **Full:** the 21k fixture, half AVIF and half JPEG, analysed into a catalog of 109 sets.
- **AVIF sets:** 880 AVIF stills made from the fixture's JPEGs at several sizes and qualities, in
  220 sets of 2 to 6 versions, 8-bit 4:2:0.
- **Scaled:** the AVIF sets' catalog 25 times over: 22,000 rows, 5,450 sets, with a cold rebuild

- **AVIF stills:** 3,300 clones of the fixture's AVIFs for View, and 998 and 199 of the fixture's
  AVIFs for the decoders, mean 6.4 megapixels.

## Hardware decoding of AVIF, for the owner to decide

The owner decided: it landed in the [second round](#the-second-round), macOS only.

AV1 decoding is most of a still's first analysis: about 80 % of a print's samples are under
`heif_decode_image`, which holds aom and libheif's conversion to RGB, and aom's entropy decoding
alone is 55 %. The file's parsing and libvips' colour and resize make up the rest.

Load 5 to 11, 2 rounds each. These come from a scratch program kept out of the tree, which runs the
libvips steps `grey_pixels` runs for a still with no alpha or profile. The planes go through
libheif's fixed-point 4:2:0 conversion, written out; from dav1d's planes, its full RGB equals what
libvips loads on 998 of 998 stills.

- **Bundle:** adds 0 bytes. `libdav1d.7.dylib` (728,064 bytes) and libavif already ship, and
  VideoToolbox is part of macOS. Windows has no VideoToolbox, so it would keep today's path or use
  dav1d.
- **Not simple, so not landed:** it needs an AVIF box reader or libavif's parser, the conversion,
  and a fallback to today's path for anything but plain 8-bit 4:2:0 without alpha, a profile or a
  turn. A closer look needs the same work: `heif_decode_image` is about 75 % of its samples.
- **Not yet known:** every still checked is the fixture's. Before prints depend on it, a run over
  the owner's library has to report how many stills take the fast path and whether each print
  matches, numbers only.

## The second round

with every input the same byte for byte. Closer looks stay on libvips, where an answer of "copy"
can only come from libaom decoding both files (see

### What the independent review changed

Closer looks read both files through libvips only, so an answer of "copy" can only come from libaom
decoding both. Prints and detail prints keep the hardware route. The hardware route reads damaged
AVIFs that libvips refuses: flipping one bit in the last 400 bytes of a made-up still's coded data,
60 times, libvips refused 59, the hardware route read all 59, and on 1 of those a closer look through
it called the damaged file a copy of the good one, and the set offered to remove a file. Now that
damaged file still gets a print and its pair still gets a closer look, but libvips cannot read it, so
the answer is "could not read", which keeps both files and is asked again at the next launch or scan
(`variant = 2` in `file_comparisons`). Without libvips no answer is stored at all.

| Owner's catalog, 3 interleaved runs | Closer looks: 1,429 answers, 2,562 files | Prints: 11,616 |
|---|---:|---:|
| Hardware prints, libvips closer looks (what ships) | 289–290 s CPU, 17.2–17.5 s | 628–641 s CPU, 49–51 s |
| Hardware for both, not kept | 119–120 s CPU, 9.0–9.8 s | 618–637 s CPU, 47–50 s |
| libvips for both | 290–292 s CPU, 17.1–25.9 s | 1,680–1,689 s CPU, 100–120 s |

- **Why closer looks gave up the hardware route.** 1,040 of 1,429 answers (73 %) are "copy", taking in
  1,929 of the 2,562 files (75 %). Confirming those through libvips cost 299–310 s CPU in earlier
  runs, no better than libvips alone, for more code.
- **Nothing the owner's library stores moved:** answers, prints and fingerprints hash the same on all
  three rows of the table. All 1,429 answers came out the same, none "could not read".
- **Damage was never visible, on either route.** A damaged AVIF whose header reads has no
  `probe_error`, so Undecodable and Won't decode miss it both ways. Through libvips it gets a
  `fingerprint_error`, which no screen shows; on the hardware route it gets a print instead, and can
  appear as a variant of its good copy, with both files kept. None of the owner's 31 failed prints
  is a still: all are MP4.
- **A re-encode now beats only the bytes it was made from, while they are held.** Of 3,766 open sets
  none changes its suggestion: no open set holds one of the 2,117 files flagged as re-encoded, and
  the 70 dismissed sets that hold one do not change either. The rule was wrong, but it changes no
  suggestion on the owner's catalog today. Those flags came from a backfill in the migration, since
  dropped: a step from before it has no `source_sha256`, so a flag on its output can never apply.

### What the second review changed

- **Spot variants off.** A set keeps one file there with no closer look, so a damaged AVIF that only
  the hardware route could print could be kept and its healthy original removed. Now the setting
  skips only the judgement of whether two pictures differ. A pair where either file could have come
  through the hardware route (an AVIF, a HEIF, or a file not yet told apart) is read through libvips
  first, and the set stays checking until it is. Any answer that read both will do; one that could not
  keeps both. Identical bytes rest on their hash, and animations and videos never take that route.
- **Every removal is compared with the file kept.** The home folder can change which version is best,
  so pictures are worked out again in the new order, and pairs not yet looked at hold the set.
- **A re-encode goes ahead of its source only past copies of that source,** never past a larger
  unrelated file.
- **Pairs that could not be read** are asked again when Tidy starts and when a scan ends. Decisions
  keep their gate, so a damaged file costs one read at each of those times and no more.

### What the third review changed

- **A duplicate goes only while the file kept is as the scan saw it.** Each Hold step of a resolution
  records its keepers' size, dates and hash, in the step's own record with no schema change. Before
  holding, each is read as the file itself is. Changed or gone, on an unmounted volume too, skips the
  step as stale, and the rescan follows. Dates alone changed, the bytes decide. `main` had this
  defect too. What this does not cover: a scan finishing in the moment before a click, so the
  catalog already has the changed keeper when the stale page's decision is drafted.
- **A first look asks once per version,** stopping at its first unanswered pair; the set offers
  nothing until it is answered, and later rounds go on from there. Every removal still rests on a
  look against a file that stays.

### What the fourth round of fixes changed

- **Paused work.** Reads, Empty to Trash and switching root never wait behind a paused job. Asked-for
  work waits by design, and now says so. Quitting no longer hides the window to wait for a change
  queued behind a paused scan or analysis. Forget asks whether it can go before holding goes to the
  Trash, which it used to empty and then refuse.
- **"Keep these" holds in any set the files later fall into,** in both Spot variants settings, for
  stills, videos and identical copies: such a pair counts as two pictures, with no look asked for.
  Over 3,766 open sets, none changes with Spot variants on, and 1 with it off, which keeps 48 kB more.
- **A decision carries what the page showed.** Files whose size or date differ from that by the time
  the plan is drafted leave that decision out, so a scan just before the click cannot pass a stale
  one. Stale files in every decision of a request refuse it with a message.

### The stall in the Keep spike

The round above could not explain a Keep spike that stopped settling for 30 s a step. It was a real
bug, older than this work, not an artefact of the spike. It is fixed.

- **Cause:** a lost event. `start_perform` starts the apply job, then waits on a task before it
  subscribes for the job's end. A Keep takes about 9 ms, so the job could finish first; `JobEvent`
  is heard once, and the waiter then waited for ever. With `change` and `change_turn` held, every
  later change queued behind it. During a stall, a sample shows nothing working: the catalog's thread
  parked, no engine thread, and `change` set on a job no longer running.
- **30 s** is the spike's own step `TIMEOUT`. The stall itself has no end: 150 s further on nothing
  had moved.
- **What the owner saw:** the decided set left the screen and its files did move, so the stuck Keep
  itself took effect. Overview and the queue froze (40,270 files shown with 40,265 in the catalog, 1,296
  sets shown), with no toast and no Undo for it. Later decisions also left the screen but only queued:
  3 decided sets were never applied in 150 s, and were lost on quitting. A quit waited on the work, so
  the first ⌘Q hid the window and left the app running (read from the code).
- **Fix:** `when_finished` answers at once for a job that has already finished. A test pins it; it
  failed before the fix.
